# Experimental lookup reason deltas

`tb-cache-delta.py` reads retained experimental `[tb-cache]` lines offline.
It never contacts a process or guest. This is a diagnostic count reader, not
another CPU backend or a performance benchmark. Production counters stay out.

The already-built instrumented4096-entry engine from producer
`cebbe89353b75367f23677cc1440380a1069297d` has the six counters from experimental
commit `6b209cfec575eee4e9dbcf3c76140e81bb93875e`. Existing fresh-worker
`IT_VCPU_ACCT=1` enables cumulative nominal1Hz dumps. Both that accounting and
the counter branches perturb execution. Do not compare its latency directly
with the uninstrumented4K/16K engine runs. Execution requires a separate guest
allocation and exact source/artifact binding; this document grants none.

The operator's boundary reader retains the entire final log and a selection:

```json
{
  "schema": 1,
  "identity": {"host_boot_id": "actual-boot", "pid": 123,
               "start_ticks": "actual-startticks", "engine_sha256": "actual-64-hex-hash"},
  "label": "first-settings-observation-window",
  "log": {"path": "/private/final-engine.log", "sha256": "actual-64-hex-hash"},
  "before": {"line_offset": 1000, "read_begin_monotonic_ns": 100,
             "read_end_monotonic_ns": 110},
  "after": {"line_offset": 2000, "baseline_eof_offset": 1900,
            "baseline_read_begin_monotonic_ns": 160,
            "baseline_read_end_monotonic_ns": 170,
            "read_begin_monotonic_ns": 180, "read_end_monotonic_ns": 190},
  "action": {"down_begin_monotonic_ns": 120, "down_end_monotonic_ns": 125,
             "last_transition_source_ns": 140, "first_complete_source_ns": 150}
}
```

Numbers are illustrative. `line_offset` is the raw byte offset of the first
`[` of that complete line in the final hashed log. Before input, retain the
latest complete counter line and read bounds. After the operator-inspected
complete target source frame, read EOF, then observe a newly appended complete
counter line starting at or after that EOF. Preserve both read intervals and
the baseline EOF. The parser verifies ordering and hashes, not the truth of
the operator's identity or image inspection assertions.

```sh
python3 contrib/portable/tb-cache-delta.py /private/selection.json > /private/delta.json
python3 tests/portable-tb-cache-delta.py
```

The log is bounded at16MiB and the selection at1MiB. Missing, malformed,
interleaved or incomplete counter lines, repeated/decreasing elapsed times,
geometry changes, uint64 overflow, decreasing counters, bad offsets/hashes and
contradictory witness ordering are refused. An unfinished run is not a pass.
The selected log must contain only one worker/counter epoch.

Each dump is generated by the owner vCPU outside `cpu_exec`, so snapshots
contain no lookup still in progress. The six meanings are:

| Counter | What it measures |
|---|---|
| `fast` | Same virtualPC, `cs_base`, flags and cflags matched the selected slot. |
| `empty` | Selected slot was NULL; startup and invalidation are both possible. |
| `pc` | Non-NULL slot contained another virtualPC: an actual hash-slot conflict. |
| `state` | Same virtualPC, but at least one `cs_base`/flags/cflags check failed. |
| `slow-hit` | Physical-address/QHT fallback returned an existing TB. |
| `slow-absent` | Fallback returned NULL. |

`fast + empty + pc + state` counts lookup calls, not all guest TB executions.
Direct chaining bypasses lookup. Misses may exceed slow results when a code-page
lookup faults/longjmps before returning. The parser retains that gap; it is not
automatically lost data. Counters remain cumulative through invalidation.

These are wider **observation-window deltas**. Native elapsed strings are
rounded to0.1s relative to accounting initialization; they are not host-monotonic
timestamps and cannot be aligned exactly by subtracting HELLO/worker start.
New append proves publication after EOF, not necessarily counter evaluation
after the target: `fprintf` can wait for stderr's lock after argument evaluation.
Likewise, outer-loop execution can delay nominal1Hz dumps. The reported ±0.1s
elapsed rounding interval is about the two native elapsed strings only; it is
not a guaranteed1s bound on action attribution. Keep input and frame source
brackets separately, and never call these exact per-action counts or CPU time.

If `pc` dominates misses, evaluate hash/associativity before another larger-cache
guess. If `state` dominates, only then consider a separate experimental split
of its three comparisons. ARM's `cs_base` is `hflags.flags2`, not a literal ASID
or x86 segment base. Never remove context checks. If `empty` dominates, existing
sparse JIT flush/invalidation snapshots can help, but they do not count every
page jump-cache clear. Any additional invalidation counters need concurrency
review because clearing can run outside the lookup-owner thread. Preserve all
physical/MMU/page/full/per-TB validity rules. None of these counts alone proves
disabled chaining, storage waits or a viable replacement execution backend.
